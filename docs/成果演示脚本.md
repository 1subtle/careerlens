## 2. 分镜与讲稿

### 00:00—01:20 项目背景

**画面：** 标题“CareerLens：AI 简历诊断与岗位匹配”，随后切到原简历与 JD 对照。

**讲稿：**

> 我们的项目是 CareerLens，面向正在准备实习或求职的学生。学生往往已经有课程、项目或实习经历，但阅读岗位描述时，很难判断哪些经历能够支持要求，哪些条件仍需确认，也不容易把已有事实写得清楚、具体。
>
> 系统把这一过程整理成一条可以复核的操作链：导入并校对简历，保存目标岗位，查看要求与经历证据，确认事实，审阅改写，最后生成独立的定向版本。这里展示的是明确标注的合成示例。我们的目标是帮助学生理解材料与岗位的关系，并保留每次修改的依据。

**字幕：** “要求有来源；判断可核对；改写留原稿”。背景调研只介绍已完成材料，不展示未经执行的问卷统计或用户满意度。

### 01:20—03:10 系统架构

**画面：** 展示系统设计方案中的架构图，再切换到源码目录和数据模型。控制单屏文字，主要标注 Next.js、FastAPI、SQLite、远程模型、本地语义检索。

**讲稿：**

> 系统基于 Resume Matcher 的固定版本继续开发。前端采用 Next.js 和 React，负责简历编辑、岗位选择、诊断审阅、图表和导出入口。前端通过同源 API 代理访问 FastAPI 后端。后端负责材料解析、要求归一、证据匹配、版本事务，以及岗位来源和模型服务适配。
>
> SQLite 保存简历、岗位、冻结快照、诊断、草稿和修改记录。诊断读取已经保存的材料，因此后来编辑简历不会覆盖原来的分析依据。采纳草稿会生成新简历版本，并保留原稿。
>
> AI 由服务端配置的模型提供，事实核验和结果校验放在后端。本地语义模型只检索相关经历候选，候选必须核对后才影响规则判断。相同代码还支持本地和网站两种模式：本地无需账号；网站通过邮箱验证码登录，每位用户使用独立数据库。图中的网站部署是源码支持的结构，实际公网部署仍需目标服务器验收。

**字幕：** “上游复用：编辑与基础导出；项目扩展：证据诊断、事实改写、岗位样本与账号隔离”。具体改动范围指向 `UPSTREAM.md`。

### 06:40—08:30 技术亮点

**画面：** 三张简短要点卡，配合规则结果明细、无来源改写反例和版本对照；最后展示测试报告。

**讲稿：**

> 第一，规则覆盖度可以复算。普通要求权重为二，加分项为一；有应用证据、仅技能提及和待确认分别有不同取值。学历和到岗条件单独呈现，因此一个较高分数不会掩盖明确的条件冲突。AI 适合度另行展示，二者含义不同。
>
> 第二，改写受到事实约束。我们先检查数字、技能、角色、成果和用途，再核对每句话的原文引用。例如，“参与问卷”不能直接扩写成“主导产品上线、提高留存”。用户仍需审阅并确认，系统才建立新版本。已有清楚的段落若只改标点，也不会被当作明显改善。
>
> 第三，版本和身份贯穿完整链路。诊断保留快照，重复采纳返回同一个版本，过期草稿会被拒绝；网站模式将账号身份延续到数据查询及 Word、PDF 导出。AI 辅助开发用于需求、设计、编码和测试材料，但每条实现结论都需要源码和运行证据支持。这里展示本轮实际执行的后端一百三十三项、前端七十项专项通过记录。

**字幕：** “规则可复算”“逐句引文与本人确认”“快照、幂等、账号隔离”“专项通过 ≠ 真实模型质量指标”。

### 08:30—09:30 关键实现思路

**画面：** BUG-01 修复链 → 测试报告 → 文档总览；最后停留项目名称与成员页。

**讲稿：**

> 一个代表性问题是原文保存：早期接口只更新结构化内容，导致原文重载后仍是旧值。修复从同步写入和版本冲突检查入手，再用独立数据库验证“保存、重载、旧窗口冲突”这三个行为。事实扩写问题也按同样的方法处理：先给出能复现的反例，再限制实现并加入回归。
>
> 当前源码和 Markdown 文档已经覆盖主流程、后端与数据库设计、测试和运行方式。后续重点是补齐真实学生材料的授权与质量评估，在目标服务器验证部署和恢复，并完成正式录制与个人报告。我们的经验是让 AI 提高整理和实现效率，同时把需求、代码和验证证据对应起来。
