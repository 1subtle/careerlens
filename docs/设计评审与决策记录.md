## 1. 评审范围与结论

CareerLens 已形成简历编辑、要求级匹配、AI 诊断、事实约束改写、独立版本与岗位样本分析的完整设计。当前架构沿用 Next.js、FastAPI 和 SQLite，支持本地个人与网站账号两种使用方式。第三天的工作重点是统一现有需求、详细设计、接口和验收依据，并据测试及真实样本反馈继续迭代。

## 2. 已落地的技术决策

表2-1 关键决策及依据

| 编号 | 决策 | 依据与影响 | 对应实现 |
| --- | --- | --- | --- |
| ADR-01 | 固定一个上游基线进行二次开发 | 保留可运行编辑与打印链路，集中完成 T5 业务 | [复用说明](../UPSTREAM.md) |
| ADR-02 | 保留 SQLAlchemy/SQLite | 当前事务、索引和初始化已围绕 SQLite 实现；课程 PostgreSQL/pgvector 为推荐工具 | `models.py`、`db_engine.py`、`database.py` |
| ADR-03 | 规则覆盖度与 AI 适合度分别呈现 | 前者可复算，后者用于语义判断；避免不同含义的分数混合 | `services/matching.py`、`services/career_diagnosis.py` |
| ADR-04 | 语义模型只提供证据候选 | 相似表述不自动证明能力，候选经核对后按规则计分 | `services/semantic.py`、`services/matching.py` |
| ADR-05 | 诊断冻结简历与 JD，人工修正产生新记录 | 历史结果可重现，材料变化后不会静默覆盖旧结论 | `routers/career.py`、`resume_snapshots`、`match_records` |
| ADR-06 | 改写按段落，采纳生成独立版本 | 用户可逐句审阅事实来源，原版与不同目标岗位版本可并存 | `services/career_ai.py`、`rewrite_records` |
| ADR-07 | 网站通过账号上下文选择独立业务库 | 旧接口也须进入同一数据隔离边界；避免仅在新接口过滤账号 | `auth.py`、`tenant_database.py`、`main.py` |
| ADR-08 | 浏览岗位与保存 JD 分开 | 用户只保存主动选择的材料；本页统计不污染持久岗位库 | `routers/recruitment.py`、`components/career/market-panel.tsx` |
| ADR-09 | 保留本地规则路径及场景化失败恢复 | 文件解析可保留原文；请求 AI 诊断失败则提示，不能伪装为成功 | `routers/career.py`、`services/matching.py`、`services/career_diagnosis.py` |
| ADR-10 | 照片与版式按简历保存，导出走已保存版本 | UI 编辑、预览、PDF/DOCX需有一致的内容与版本边界 | `services/resume_photo.py`、`services/resume_docx.py`、`pdf.py` |

上表未将原方案中的未来规划视为已经部署。真实域名、SMTP 邮件送达、容器与 HTTPS 验收继续按部署清单执行。
